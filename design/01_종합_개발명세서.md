# JB School 업무 자동화 플랫폼: 7개 웹앱 통합 개발 명세서

- 문서 버전: 1.0 (설계 초안)
- 기준일: 2026-10-31
- 대상: 중학교 교직원(PC 중심), 학교 관리자, 업무담당자, 수학 교사
- 개발 목표: 반복적인 조사·취합·점검·기록·문서 업무 시간을 절감하되, 공식 승인·성적 확정·학생부 입력은 기존 승인된 행정 시스템과 교사가 담당
- 운영 형태: **공통 포털 + 온라인 협업형 4개 + 오프라인 로컬형 3개**. 7개 모듈은 독립 실행 가능해야 함.
- 상태: 실무 검토를 위한 구현 명세. 학교의 보안·개인정보·학업성적관리 규정 확인 전 실제 개인정보로 운영 금지.

## 0. 설계의 핵심 결정 사항

1. **공통 UX**: PC 우선, 큰 글씨(기본 16px), 한 화면 한 가지 주작업, 저장 여부 상시 표시, 완료 항목은 즉시 '완료 보관함'으로 이동, 명시적 실행 취소 제공.
2. **공통 사용자/부서/학년도/템플릿/알림/활동 로그**는 공유한다. 학생 성적·학생부 초안은 공유 사용자 DB와 논리적으로도 기술적으로도 분리한다.
3. **온라인 업무**(회신·회의·연수·인수인계): 사용자 인증, 서버 측 권한 검사, 데이터베이스, 감사 로그 필요. 단순 공개 URL과 화면 비밀번호만으로 보호하지 않음.
4. **오프라인 업무**(채점·기록 검토·문서 점검): PWA 또는 로컬 실행으로 구현. 기기 내 데이터 처리, 외부 전송 기본 차단. 브라우저 저장이 곧 안전한 암호화 저장을 뜻하지 않으므로 민감 데이터는 가급적 무저장 모드, 저장이 필요하면 사용자가 승인한 암호화 파일 또는 기관이 승인한 보호 저장소를 사용.
5. **공식 시스템 대체 금지**: NEIS/K-에듀파인/공식 연수 이수증/전자결재를 사칭하거나 승인 없는 자동 업로드·연동을 시도하지 않음. 결과는 사전 검토용·내보내기용.
6. **버전 관리**: 학교 업무 체크리스트와 학생부 검토 규칙은 학년도·시행 지침·출처·유효기간을 기록한다. 불확실한 판단은 '검토 필요'로만 표시.
7. **HWP 지원 전략**: HWPX는 구조화 파싱 가능 범위부터 지원하며, 구형 HWP 바이너리 지원은 변환 또는 별도 모듈의 검증 이후 추가. 이미지 기반 PDF OCR은 로컬 OCR 엔진을 별도로 탑재했을 때만 지원.

## 1. 공통 포털 정보 구조

### 1-1. 내비게이션

```
JB School
├─ 오늘 할 일: 내 담당/마감 임박/확인 필요/보관함
├─ 소통·취합
│  ├─ 교직원 회신·취합
│  ├─ 회의·협의회
│  └─ 교직원 연수·참석
├─ 수업·평가(로컬 도구, 별도 저장)
│  ├─ 수행평가 채점·피드백
│  └─ 학기말 기록 검토
├─ 행정·자료
│  ├─ 공문·제출서류 점검
│  └─ 업무 인수인계
└─ 관리: 교직원/조직/권한/서식/학년도/보관 정책/감사 이력
```

### 1-2. 핵심 공통 화면

- **통합 홈**: 오늘 마감, 미회신 요청, 내가 맡은 결정 후속조치, 예정된 회의와 연수, 최근 문서, 완료 보관함. 개인정보가 포함되는 로컬 앱의 데이터는 홈으로 복사하지 않음.
- **업무 목록**: 검색·상태 필터·담당자·마감일·정렬, 선택한 항목 일괄 완료/보관, '완료'는 기본 목록에서 숨김.
- **상세 화면**: 상단 제목/상태/마감/책임자, 중앙 실제 작업, 오른쪽 도움말·활동 이력(사용자 선택으로 접기).
- **설정**: 학교명, 학년도, 부서, 담당자, 교육청·학교 규칙 버전, 테마, 접근성, 내보내기 형식.

### 1-3. 공통 UI 규약

- 데스크톱 기준 좌측 메뉴 232px, 중앙 컨텐츠 최대폭 1280px; 1366×768에서도 주 기능 이용 가능.
- 입력 글씨 16px 이상, 표 14–15px 이상; 클릭 영역 최소 40×40px(권장 44×44px), 키보드 탭·Enter·Esc 제공.
- **모든 저장 작업**: '저장 중' → '저장 완료(시각)' → '저장 실패: 재시도' 상태 구분.
- 취소선만 남기는 대신 완료 항목을 목록에서 제거하고 '완료 보관함'에서 복원할 수 있게 함.
- 장문의 입력은 초안 저장(온라인은 서버, 민감 오프라인은 정책에 따른 보호 저장). 저장·보관·삭제의 차이를 명확히 표시.
- 상태 색상과 문자 동시 표시: 요청 전 / 진행 중 / 미회신 / 완료 / 마감 / 취소. 색상만으로 구분하지 않음.
- 교직원 20대~60대 사용성: 익숙한 용어 '회신', '취합', '결과 내려받기', '완료 보관함'; 과한 팝업 최소화.

## 2. 모듈 A: 교직원 회신·취합 관리

### 문제 및 목표

교직원에게 신청·의견·확인 요청을 보낸 뒤 회신 여부와 결과를 일일이 취합하는 과정을 단일 업무로 처리. 연수 신청과 회의 참석조사에도 재사용하는 **핵심 공통 엔진**.

### 사용자·권한
- 관리자: 학교 조직과 권한 설정; 전체 요청 열람 범위는 업무상 필요한 범위로 제한.
- 요청 작성자: 요청 작성, 대상 지정, 배포, 미회신 확인, 결과 다운로드.
- 응답자: 본인에게 배정된 요청 확인·회신·수정(마감 전 허용 시).
- 열람자: 권한을 받은 집계 통계만 조회. 익명 응답은 본문과 응답자 연결을 원천적으로 저장하지 않는 방식으로 구현.

### 핵심 사용 흐름
`요청 만들기 → 유형/질문/대상/마감 선택 → 배포 → 응답 → 자동 집계 → 미회신자 재안내 → 마감·결과 다운로드 → 보관`

### MVP 기능
1. 요청 유형: 참석 여부, 희망 조사(단일/복수), 짧은 의견, 파일 제출 여부, 열람 확인.
2. 질문 유형: 예/아니요, 단일 선택, 복수 선택, 짧은 문장, 날짜, 숫자, 파일 첨부(승인된 저장소로만).
3. Excel/CSV 직원 명단 불러오기 및 중복 이메일·누락 수신 대상 검증. 실명 회신과 익명 회신 분리.
4. 배포 URL/QR 및 안내문 복사. **링크를 안다고 누구나 제출하는 방식 금지**: 인증 기반 또는 기관이 승인한 일회용 토큰.
5. 요약: 전체 대상, 회신, 미회신, 응답률, 질문별 분포, 대상자별 진행 상태(실명 조사 한정).
6. 마감 전 알림 초안과 일괄 복사, 발송 로그; 실제 자동 발송은 기관 이메일/메신저 승인된 연결 이후.
7. 마감 후 읽기 전용, 담당자가 재개 가능, 변경 이력 보존, XLSX/CSV 출력.
8. '미회신'은 실제 요청 전달 성공 여부와 별개. 전송·열람 확인이 없는 경우 이를 임의로 '안내 완료'로 처리하지 않음.

### 화면 구성
- **목록/현황**: 카드(진행 중, 오늘 마감, 취합 완료), 요청 표, '새 회신 요청' 버튼.
- **요청 작성 마법사**: ①요청 정보 ②질문 ③대상 ④미리보기/배포.
- **응답자 화면**: 제목, 안내, 마감, 문항, 제출 버튼, 제출 결과, 재수정 가능 여부.
- **결과 화면**: 응답률, 질문별 집계, 미회신 목록, 재안내 문구, XLSX 다운로드.

### 데이터 모델
`response_campaign(id,title,type,owner_id,unit_id,opens_at,due_at,visibility,status,anonymous,revision)`
`response_question(id,campaign_id,kind,label,required,choices_json,sort_order)`
`response_target(id,campaign_id,user_id,delivery_status,delivery_at)`
`response_submission(id,campaign_id,respondent_id_or_null,submitted_at,revision)`
`response_answer(id,submission_id,question_id,value_json)`
`response_reminder(id,campaign_id,target_id,channel,initiator_id,sent_at,delivery_result)`

### 핵심 규칙/예외
- 응답률 = 유효 제출자 수 / 대상자 수 × 100. 철회·중복 제출·미배포 대상은 정책에 맞게 제외.
- 익명 설문은 미회신자 추적과 **동시에 제공할 수 없음**(별도의 익명 제출 여부 토큰 관리에도 재식별 위험 점검 필요).
- 재개 마감 시 버전 변경 이력 표시. 마감일 변경은 대상자에게 별도 안내 대상.
- 인터넷 끊김 시 미전송 응답을 '제출 완료'로 표시하지 않음.

### MVP 완료 조건
- 40명 대상 조사 생성 → 3명 회신 → 미회신 37명 표시 → 중복 회신 제어 → XLSX 다운로드의 행 수·내용이 원본과 일치.
- 작성자 아닌 사용자의 전체 응답 열람·수정 거부, 마감·재개 기록 유지.

## 3. 모듈 B: 수행평가 채점·피드백 (오프라인 분리형)

### 문제 및 목표
중학교 수학 서술형·논술형의 채점요소별 점수 입력, 규정에 맞는 합계 확인, 교사 검수형 피드백 생성. 학교 공식 성적 처리 전에 **교사용 보조 도구**로 사용.

### MVP 기능
1. 학년도/학기/학년/반/과목/평가명, 평가 반영 비율, 기본점수, 만점, 채점 단위 설정.
2. 루브릭 편집: 문항별 요소(예: 개념 이해, 논리 전개, 계산 정확성), 점수 급간, 단계별 설명, 부분점수 정책.
3. 학생 명단 CSV/XLSX 불러오기: 학번/이름 또는 익명 식별키. 동일 학번 중복 및 반 불일치 경고.
4. 한 화면 채점: 왼쪽 학생 목록/상태, 중앙 답안별 채점 카드, 오른쪽 총점/미채점 경고/피드백.
5. 기준표 버튼으로 점수 선택, 자동 합산 및 최대점수 검증, 결시·인정·미채점 별도 표시(임의로 0점 처리하지 않음).
6. 루브릭이 확정된 평가에서는 기준 변경 시 경고 및 버전 분리. 점수 변경 감사 이력은 로컬 보호 저장.
7. 피드백 문구는 기준표와 선택한 관찰 사실에서 조합, 교사 최종 수정/승인. 점수나 수행 근거 없이 학생 능력을 단정하는 생성 금지.
8. XLSX/CSV 결과, 인쇄용 채점표·학생별 피드백. NEIS 양식은 검증된 템플릿에만 매핑.
9. 오프라인, 외부 전송 없음. 평문 자동저장 기본 비활성; 암호화 백업 파일 지원.

### 화면 구성
- 평가 대시보드 → 평가 만들기(루브릭) → 학생별 채점 → 채점 현황/오류 검토 → 결과 내보내기.
- 채점 화면: 학생 전환 단축키, 현재 문항 강조, 미채점 여부, 이전/다음 학생, 저장/내보내기 버튼.
- 집계: 점수 분포, 채점 완료율, 문항별 평균, 내보내기 유효성 검사.

### 로컬 데이터 모델
`assessment(id,year,term,grade,subject,title,max_score,base_score,weight,policy_version,rubric_version)`
`student(id,school_local_key,grade,class_no,number,name_optional)`
`rubric_criterion(id,assessment_id,item_no,label,max_points,steps_json,sort_order)`
`score_entry(id,assessment_id,student_id,criterion_id,points_or_null,status,reason,updated_at)`
`feedback(id,assessment_id,student_id,text,teacher_approved,updated_at)`
`score_history(id,assessment_id,student_id,criterion_id,old_value,new_value,changed_at)`

### 핵심 규칙/예외
- 저장 점수는 부동소수 오차를 피하도록 정수 단위로 관리(예: 0.5점 단위 → 정수 1). 표시 시 환산.
- 기본점수·인정점·결시 처리 규칙은 학교 학업성적관리규정에 따르며 일괄 자동 판단하지 않음.
- 루브릭 변경 후 이전 기록이 자동으로 조용히 재계산되지 않도록 확정/재산출 확인을 별도 요청.
- 학생명 없는 연습·익명 데모 모드 우선 제공.

### 완료 조건
- 30명 × 4개 기준 채점, 미채점 1명 식별, 수정 이력, 합계 검증, Excel 내보내기·재불러오기 무손실.
- 로컬 오프라인에서 정상 작동; 네트워크 감시 테스트에서 외부 요청 없음.

## 4. 모듈 C: 회의·협의회 관리

### MVP 기능
1. 회의 구분: 교과협의회, 학년협의회, 인사자문위원회, 업무협의회 등.
2. 회의 생성: 일시·장소·주관·참석 대상·안건 제출 기한·자료 첨부·사전 안내 여부.
3. 안건 공모, 안건 작성자, 관련 첨부, 협의 내용, 결정/보류/추가 검토 상태.
4. 참석자 표시(참석/불참/대리/확인 필요), 정족수·의결 기준은 학교 규정에 따라 설정 또는 비활성.
5. 회의록 템플릿: 기본정보, 참석자, 안건별 논의 요지, 결정사항, 후속 조치, 담당·기한.
6. 회의록 검토 요청 및 확인 이력. **법적으로 요구되는 서명·결재를 대체하지 않음**.
7. 후속 조치는 '오늘 할 일'로 이동, 완료 시 회의록에 결과 자동 표시.
8. 회의록/참석부/결정사항 목록을 PDF/DOCX/XLSX/HWPX(검증 후)로 출력.

### 화면 구성

`meeting(id,title,kind,organizer_id,starts_at,ends_at,location,status,notice_status,minutes_version)`

## 5. 모듈 D: 학기말 기록 검토 도우미 (오프라인 분리형)

### 범위·제약
담임·교과교사가 작성한 **학교생활기록부 초안**의 형식·중복·검토 필요 표현을 찾아주는 도구. 법규 적합성의 자동 판정이나 NEIS 원본 수정은 하지 않음. 규칙은 학년도, 학교급, 항목, 출처를 구분.

### MVP 기능
1. 학생 식별정보를 제거한 텍스트 검토 또는 사용자 승인 시 로컬 파일 불러오기(.txt/.csv/.xlsx, HWPX 가능 범위).
2. 항목 구분: 교과 세부능력 및 특기사항, 창의적 체험활동의 세부 영역, 행동특성 및 종합의견 등 학교에서 사용하는 검토 항목으로 구성.
3. 동일 문구·유사 문장 탐지: 같은 학생 내 반복, 학생 간 지나치게 비슷한 문장(학급 내부에서만), 과도한 상투 표현.
4. 맞춤법·띄어쓰기 점검은 내장 규칙/사전 범위에서 수행하며, 지원하지 않는 언어 교정은 명시.
5. 입력 금지 또는 주의 표현의 후보 탐지, 학생부 항목별 검토 규칙, 고유명사·날짜 등 패턴 경고.
6. 텍스트 길이/바이트 수 확인: UTF-8 측정 등 계산 방식과 설정값을 분명하게 표기. NEIS 허용 길이와 같다고 단정하지 않음.
7. 결과 표시: 오류 가능성(높음), 검토 권고(중간), 문체 제안(참고). 문장 자동 수정 대신 원문·제안 나란히 표시.
8. 검토 확인표와 수정 비교표 내보내기. 익명 키 기반 작업 모드 및 민감 데이터 자동 소거.
9. 지침 출처/버전(2026 중학교 학생부 기재요령, 학교 내 관리규정 등)을 룰별로 저장. 규칙 없음→'판단 불가'.

### 화면 구성
①자료 불러오기 → ②대상 선택 → ③검토 결과(왼쪽 원문, 오른쪽 이슈 카드/근거) → ④수정 비교 → ⑤검토표 출력.

### 로컬 데이터 모델
`record_batch(id,school_level,academic_year,term,source_type,created_at)`
`record_entry(id,batch_id,student_key,field_type,text_original,text_edited,source_ref)`
`record_rule(id,rule_code,year,school_level,field_type,severity,kind,pattern_or_config,source_title,source_url,valid_from,valid_to)`
`record_finding(id,entry_id,rule_id,span_start,span_end,message,suggestion,status,reviewed_by_local)`
`record_revision(id,entry_id,before_hash,after_hash,changed_at)`

### 주의 및 완료 조건
- 2026학년도 중학교 기재요령이 교육부에서 2026-02-19 공개되었음을 규칙 버전 메타데이터로 반영.
- **학생부 중복 기재·봉사시간 인정·기재 가능 여부** 등은 규칙에 따라 교사가 확인해야 하므로 AI가 '가능/불가'로 자동 단정하지 않음.
- 원문과 수정 후 문자열의 차이를 강조, 확인 완료 표시는 실제 사용자가 클릭해야 함.
- 데이터가 서버로 전송되지 않는다는 것을 브라우저 네트워크 검사로 확인.

## 8. 모듈 G: 공문·제출서류 점검기 (오프라인 분리형)

### MVP 기능
1. 문서 유형별 체크리스트: 내부 결재 기안, 행사계획, 연수 결과보고, 표창 추천·공적조서, 물품 품의, 협의회 회의록 등. 규칙은 사용자/학교 관리자 수정 가능.
2. 파일 불러오기: PDF 텍스트, DOCX, XLSX, HWPX(지원 범위). 구형 HWP·스캔 이미지의 텍스트 추출 불가 시 수동 입력/변환 안내.
3. 필수 항목 검토: 제목·시행일·대상·예산/집행계획·담당·붙임 번호·첨부파일 수·결재선 검토 체크(실제 전자결재 확인은 수동).
4. 조건부 규칙: 예산 포함 시 예산항목/견적서 여부, 행사 시 안전계획/안내문 여부 등. **학교별 운영지침과 업무 종류에 따라 설정**, 보편적 법적 의무로 단정하지 않음.
5. 금액 합계·단가×수량, 날짜 모순, 첨부번호 중복/누락, 이름 표기 일치 점검.
6. 품의꾸러미 결과를 **파일로 가져와** 점검. 기존 품의꾸러미 파일 처리 로직과 동형 연계하되 임의의 DB 직접 연결 없음.
7. 결과: '확인됨 / 확인 필요 / 확인 불가 / 해당 없음'으로 표시. 누락목록, 근거, 수정 메모, 점검 완료표 PDF/XLSX.
8. 보안 설정: 로컬 처리, 자동 업로드 없음, 내용은 로그에 저장하지 않음.

### 화면 구성
문서 종류 선택 → 파일/첨부 등록 → 체크리스트 검증 → 경고별 원문 위치·수정 확인 → 제출 전 점검표 내보내기.

### 완료 조건

## 9. 공유 데이터·권한·서비스 설계

|---|---|---|

| academic_terms | id, year, semester, starts/ends | 학년도 관리 |

| outbox_messages | id, recipient_id, channel, status, attempted_at | 안내/발송 이력 |

### 9-2. 권한 정책

- 사용자 권한: 학교 관리자 / 업무 관리자(모듈·부서별) / 담당자 / 일반 교직원 / 읽기 전용.
- **서버에서 매 요청마다 업무 범위를 검사**; 프론트에서 버튼을 숨기는 것만으로 권한 통제하지 않음.
- 직원 소속이 바뀌면 기존 개인별 접근권한을 재계산하고 과거 기록은 별도 업무 위임 정책으로 관리.
- 감사 로그에는 사용자·시각·행위·대상·결과를 남기되, 응답 내용·학생정보·첨부 원문은 넣지 않음.
- 저장 기간/삭제 절차는 기관 정책에 맞춰 설정. 공적 보존 의무가 있는 기록을 임의로 자동 삭제하지 않음.

### 9-3. 기술 선택(제안)

| 계층 | 온라인 협업형 | 오프라인 로컬형 |
|---|---|---|
| 프런트 | React+TypeScript+Vite 또는 검증된 동등 프레임워크 | 공통 UI + PWA |
| 인증 | 교육기관 승인 인증/SSO 우선, 없으면 별도 안전한 인증 | 파일/로컬 앱의 열기 보호 및 장치 정책 |
| 저장 | 기관 승인 서버/DB(PostgreSQL 등) | 메모리/보호된 로컬 저장/암호화 백업 |
| 데이터 검증 | 서버 검증·트랜잭션·감사 이벤트 | 로컬 스키마 검증·무결성 검사 |
| 첨부 | 접근권한이 있는 보호 스토리지 | 메모리에서 처리 후 사용자가 저장 선택 |
| 파일 출력 | XLSX/PDF/DOCX/HWPX 검증 후 | XLSX/PDF/DOCX/HWPX 검증 후 |
| 배포 | 기관 승인 HTTPS 도메인 | HTTPS PWA 설치 또는 정적 로컬 번들 |

- GAS/Google Sheets는 **승인된 비민감 파일로 제한한 프로토타입**에는 유용하지만, 민감 직원·학생 데이터를 다루는 정식 시스템에 자동 채택하지 않음.
- GitHub Pages는 공개 배포용 정적 소스·샘플에만 사용하고 개인정보 DB/키를 게시하지 않음.
- 포털 연결 시 링크만 먼저 통합. 인증·권한·저장을 검증한 후 API 연동 확장.
- 오프라인 PWA 캐싱은 앱 코드·엔진만; 민감 문서 및 결과를 서비스 워커 캐시에 남기지 않음.

### 9-4. 앱 간 연결 이벤트

- `response.campaign_due` → 통합 홈의 마감 업무
- `response.submission_received` → 요청자 집계 업데이트
- `meeting.action_assigned` → 내 할 일 생성
- `meeting.action_completed` → 회의 상세에 완료 상태 반영
- `training.enrollment_closed` → 연수 담당자의 집계 업무
- `handover.item_accepted` → 업무 책임자 변경 요청(관리자 승인 필요)
- 채점·학생부 검토 결과는 **이벤트로 내보내지 않음**(민감 학생 데이터 분리).

## 10. 개발 우선순위 및 일정 계획

**가치 기준**: 반복 업무 감소(35%), 기존 앱과 결합 효과(25%), 학기말 긴급성(20%), 구현 용이성(10%), 보안·운영 위험(10%). 점수는 설계상 상대평가로, 현장 사용자 테스트 뒤 조정.

|---:|---|---|---|---|
| 1 | 회신·취합 | 요청/응답/미회신/엑셀 | 알림 자동화/익명 설문 | 인증·조직·권한 |
| 2 | 학기말 기록 검토 | 로컬 텍스트/중복/길이/검토표 | HWPX·규칙 패키지 확대 | 로컬 데이터 격리·규칙 출처 |
| 3 | 수행평가 채점 | 루브릭/점수/피드백/엑셀 | 분포 분석·검증된 출력 템플릿 | 평가 규칙 확인·암호화 저장 |

| 7 | 업무 인수인계 | 업무 카드/매뉴얼/인계 확인 | 연간 일정 자동 제안 | 공통 조직·할 일 |

### 권장 빌드 단계 (기간은 인력·승인에 따라 조정)

- **단계 0 — 공통 기반**: 공통 디자인 시스템, 테스트 계정·역할, 데이터 모델, 업무 목록·보관함, 감사 이벤트, Excel 내보내기.
- **단계 1 — 첫 번째 실사용 검증**: 회신·취합. 실제 개인정보 없는 더미 직원 20~40명으로 마감·중복응답·권한 테스트.
- **단계 2 — 독립 오프라인 도구**: 기록 검토와 채점. 실데이터 사용 전 네트워크 전송 제로, 백업/복구, 계산 무결성 시험.
- **단계 3 — 공동 업무 확장**: 회의·연수. 기존 회신 엔진과 공통 업무 이벤트 재활용.
- **단계 4 — 문서·지식 관리**: 공문 점검, 인수인계, 포털 링크, 매뉴얼, 장기 보관·복원 절차.

### 첫 스프린트(구현 우선순위)

1. 공통 UI 골격/네비게이션/접근성
2. 학교·부서·교직원 더미 데이터와 역할
3. 회신 요청 생성/문항/대상/마감
4. 본인 인증 응답/제출 중복 및 수정 정책
5. 응답률·미회신 현황·XLSX 출력
6. 완료 보관함·상태 필터·감사 이벤트
7. 보안/장애/모바일/PC 테스트

## 11. 공통 수용 기준 및 테스트

### 보안
- [ ] 서로 다른 부서 사용자가 권한 밖 조사/회의/연수 정보에 접근할 수 없음.
- [ ] 익명 조사 결과에서 제출자 식별값·접속정보를 노출하지 않음.
- [ ] 학생정보를 포함한 평가·학생부 원문이 네트워크로 송신되지 않음.
- [ ] 다운로드 파일 및 백업 파일에 필요한 데이터만 포함됨.
- [ ] URL 공유만으로 권한 없는 사용자가 데이터 열람·수정 불가.
- [ ] 비밀번호·API 키·접근 토큰이 GitHub/정적 HTML에 포함되지 않음.

### UX/복원
- [ ] 1366×768 및 1920×1080에서 메뉴/표/버튼 잘림 없음.
- [ ] 모든 입력을 키보드로 완료 가능, 대화상자 Esc 닫기 가능.
- [ ] 저장 실패 시 명확한 오류와 재시도; 저장 전후 상태 표시.
- [ ] 완료 항목은 기본 목록에서 숨겨지고 보관함에서 복원 가능.
- [ ] Excel의 0·빈 셀·한글·쉼표·줄바꿈·특수문자가 손실 없이 처리됨.
- [ ] DB 백업 및 복원 실험에서 건수·해시·권한이 일치함.

### 성능(목표치, 테스트 이후 재조정)
- 일반 업무 목록 1,000건 수준에서 검색·필터가 사용에 지장이 없을 것.
- 학급 30명, 평가 요소 10개 수준에서 키보드 중심 채점이 지연 없이 작동할 것.
- 교직원 100명 규모 조사에서 중복 응답·동시 제출 오류를 방지할 것.

## 13. 개발 에이전트(Claude/Codex)에 전달할 작업 지시

> 이 명세서를 기준으로 JB School 업무 포털을 만들어라. 기존 JB WebApps/품의꾸러미/학교 업무 브리핑은 임의로 수정하지 말고 먼저 읽기 전용으로 확인하고 링크 연동만 제안하라. 공통 컴포넌트와 7개 모듈을 명확히 분리하고, 온라인 4개 모듈은 서버 측 인증·권한 검증이 없는 상태에서 실사용 모드로 배포하지 말아라. 로컬 3개 모듈은 샘플 데이터만으로 시험하고, 민감 데이터가 네트워크나 캐시에 남지 않게 하라. 첫 번째 완성물은 '회신·취합' MVP이며, 20~40명 더미 데이터와 접근성·권한·동시 제출·엑셀 테스트를 통과시켜라. 다음으로 학생부 기록 검토 MVP와 수행평가 채점 MVP를 독립 오프라인 번들로 제작하라. 각 개발 단계에서 실행 방법, 알려진 제한, 자동 테스트 결과, 수동 검증이 필요한 부분을 기록하라.
